# Custom Routing Provider Specification

## Purpose

Define a future in-house routing provider that can replace OpenRouteService through the existing `RoutingProvider` abstraction while supporting polygon avoidance for flood-aware route planning.

## Provider Goal

The custom provider must compute a route between two WGS84 coordinates and avoid supplied flood-risk polygons when possible.

Minimum behavior:
- accept start/end coordinates as latitude/longitude
- accept optional GeoJSON `Polygon` or `MultiPolygon` avoid geometry
- return a GeoJSON `FeatureCollection` containing one route `LineString`
- expose provider-specific error classification for retry/fallback behavior
- fail with actionable errors when no route can be found

## Provider Registration

The provider should be selected with:

```bash
ROUTING_PROVIDER=custom
```

Implementation requirements:
- add a `CustomRoutingProvider` class implementing `RoutingProvider`
- register `custom` in `routing_service.get_routing_provider()`
- keep OpenRouteService available as `ROUTING_PROVIDER=openrouteservice`
- keep the `/route/avoid-flood-high-risk` API response shape unchanged

## Data Sources

The provider needs a routable road graph.

Preferred source:
- OpenStreetMap road network data
- extract scope should match the deployment area, initially Europe or the currently configured operating region

Local storage requirements:
- graph data must be stored under a configurable data path
- graph version/date should be recorded for diagnostics
- startup should fail clearly if the selected provider has no usable graph data

Future configuration:
- `CUSTOM_ROUTING_GRAPH_PATH`
- `CUSTOM_ROUTING_GRAPH_METADATA_PATH`
- `CUSTOM_ROUTING_OSM_PLACE`
- `CUSTOM_ROUTING_OSM_NETWORK_TYPE`, default `drive`
- `CUSTOM_ROUTING_SIMPLIFY_GRAPH`, default `true`
- `CUSTOM_ROUTING_PROFILE`, default `driving-car`
- `CUSTOM_ROUTING_MAX_DISTANCE_METERS`
- `CUSTOM_ROUTING_SNAP_RADIUS_METERS`

## Graph Ingestion

Implemented graph ingestion lives in `api/osm_graph_ingestion.py`.

Behavior:
1. Resolve settings from `api.config`.
2. Download an OpenStreetMap graph with OSMnx.
3. Prefer `CUSTOM_ROUTING_OSM_PLACE` when set.
4. Otherwise download by the configured Europe bounding box: `EU_MIN_LON`, `EU_MAX_LON`, `EU_MIN_LAT`, `EU_MAX_LAT`.
5. Persist the graph as GraphML at `CUSTOM_ROUTING_GRAPH_PATH`.
6. Persist metadata JSON at `CUSTOM_ROUTING_GRAPH_METADATA_PATH`.

Metadata includes:
- `source=openstreetmap`
- graph adapter name and version
- creation timestamp
- graph path
- OSM source area
- network type
- simplification flag
- node count
- edge count

Operational command:

```bash
python -m api.osm_graph_ingestion
```

Failure conditions:
- missing OSMnx dependency raises an install-oriented `RuntimeError`
- empty downloaded graph raises `RuntimeError`
- OSMnx download/network failures propagate to the caller

## Avoid Polygon Semantics

Input avoid geometry:
- GeoJSON `Polygon` or `MultiPolygon`
- coordinates in EPSG:4326
- may represent merged high-risk flood polygons generated by the ingestion pipeline

Required handling:
1. validate geometry shape and coordinate ranges
2. project geometry into the graph's working CRS when needed
3. identify graph edges intersecting or contained by avoid polygons
4. exclude blocked edges from route search, or assign a prohibitive traversal cost
5. return metadata indicating whether avoidance was applied

Recommended behavior:
- clip or simplify very large avoid polygons before graph-edge filtering
- cache edge-blocking results for repeated polygons when feasible
- treat invalid or unsupported avoid geometry as an avoid-area error so existing fallback logic can retry with fewer polygons

## Routing Algorithm

Initial implementation should use a proven graph algorithm rather than custom pathfinding logic beyond integration code.

Expected flow:
1. load road graph for the configured profile
2. snap start/end points to nearest routable graph nodes or edges
3. build an avoidance mask from supplied polygons
4. run shortest path with distance or travel-time weights
5. convert resulting graph path to GeoJSON `LineString`
6. include summary properties such as distance and duration when available

Acceptable engines:
- NetworkX for a simple first implementation
- igraph or rustworkx if performance becomes a problem
- a local routing engine wrapper if it still conforms to `RoutingProvider`

## Error Classification

The custom provider must map internal failures into the existing fallback categories.

Avoid-area error:
- invalid avoid geometry
- avoid geometry too large to process within configured limits
- avoidance removes too much of the graph to evaluate safely

Unroutable point error:
- start or end cannot snap to the graph within `CUSTOM_ROUTING_SNAP_RADIUS_METERS`
- snapped point is isolated for the selected profile

Distance-limit error:
- requested route exceeds `CUSTOM_ROUTING_MAX_DISTANCE_METERS`
- graph search is rejected before execution due to configured bounds

Other provider failures:
- graph missing or corrupt
- unexpected graph/search errors
- serialization failures

## Response Contract

The provider `route(...)` method returns:

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "LineString",
        "coordinates": [[14.5058, 46.0569], [15.9819, 45.8150]]
      },
      "properties": {
        "summary": {
          "distance": 12345.0,
          "duration": 900.0
        },
        "provider": "custom"
      }
    }
  ]
}
```

The surrounding route endpoint still adds:
- `artifact_path`
- `high_risk_polygon_count`
- `avoidance_polygon_count`
- `using_avoid_polygons`
- `using_custom_radiuses`
- optional `warning`

## Performance Requirements

Baseline targets for regional graphs:
- route search should complete in under 2 seconds for ordinary routes
- avoid polygon edge filtering should complete in under 5 seconds for selected high-risk polygons
- provider should avoid reloading graph data per request

Large deployment targets:
- graph data should be loaded once at process startup or lazily cached after first request
- spatial index should be used for polygon-to-edge intersection checks
- route search should have a configured timeout and return a provider failure on timeout

## Testing Requirements

Unit tests:
- provider registration via `ROUTING_PROVIDER=custom`
- valid route without avoid polygons
- valid route with avoid polygons blocking one path and forcing an alternate path
- invalid avoid polygon maps to avoid-area error
- unsnappable start/end maps to unroutable-point error
- route beyond max distance maps to distance-limit error

Integration fixture:
- include a tiny synthetic graph with two possible paths
- include one polygon that blocks the shorter path
- assert returned route uses the longer unblocked path

API compatibility:
- existing `/route/avoid-flood-high-risk` tests should pass with the custom provider via monkeypatched fixture graph
- response shape must remain compatible with frontend route rendering

## Open Questions

- Whether graph data is built offline during deployment or lazily downloaded/prepared by the application.
- Whether travel-time weights are required initially or distance-only routing is acceptable.
- Whether polygon avoidance should fully exclude roads or apply a high penalty to allow emergency fallback routes.
- Whether routing profiles beyond `driving-car` are needed.
